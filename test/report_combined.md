#### 4.3 数据解读

**为什么串行（2.1 节）所有 workers 配置 TTFT 几乎相同，而并发（4.3 节）差异巨大？**

串行测试时并发 = 1，同一时刻永远只有 1 个请求在处理。无论有 1 个还是 128 个 worker，都只有 1 个 worker 在干活，其他全部闲置，因此所有配置的 TTFT 均为 ~105ms，这是正确的。

而并发 = 50 时，50 个请求同时到达。workers-1 的所有请求挤在同一个 Python event loop 中，受 GIL 和 event loop 调度限制，后到的请求必须等待前面的请求被分配到 event loop 才能开始处理，导致 P95 飙升到 733ms。workers-64 则将 50 个请求分发到 50 个独立进程，每个进程只处理 1 个请求，几乎零排队，P95 降到 229ms。

| 场景 | workers 优势 | 原因 |
|------|-------------|------|
| 串行（并发=1） | 无差异，均 ~105ms | 只有 1 个请求，多进程毫无意义 |
| 低并发（并发=5） | 微弱，差 10~30ms | async I/O 基本够用 |
| 高并发（并发=50） | 巨大，差 500ms+ | 多请求争抢 event loop，多进程分流优势明显 |

**表格中的两个"反常"数据点解释：**

1. **128/128 的 workers-16（394.1ms）比 workers-4（284.8ms）差**：两者 Mean 接近（189 vs 174ms），但 workers-16 的 Stdev 更高（96.9 vs 72.2ms）。16 个进程在 CPU 调度上产生更多随机性，个别请求偶发延迟飙高，将 P95 拉高。512/512 场景中此现象消失，因为长请求（15.5s）将进程切换开销均摊到可忽略的程度。

2. **512/512 的 workers-128（257.2ms）比 workers-64（198.7ms）差**：128 个进程的 OS 调度和 uvicorn load balancer 选择开销过大。Worker 数远超并发数（128 >> 50）时，进程管理开销反而增加了延迟。

**Proxy vs Direct 对比（并发=50 P95）：**

| 配置 | 128/128 Proxy | 128/128 Direct | Proxy 开销 | 512/512 Proxy | 512/512 Direct | Proxy 开销 |
|------|-------------|--------------|-----------|-------------|--------------|-----------|
| workers-1 | 733.5ms | 201.2ms | +532.3ms | 508.6ms | 226.1ms | +282.5ms |
| workers-4 | 284.8ms | 201.2ms | +83.6ms | 406.5ms | 226.1ms | +180.4ms |
| workers-64 | 229.9ms | 201.2ms | +28.7ms | 198.7ms | 226.1ms | **-27.4ms** |
| workers-128 | 191.4ms | 201.2ms | **-9.8ms** | 257.2ms | 226.1ms | +31.1ms |

workers-64/128 时 Proxy P95 甚至低于 Direct，因为多 worker 进程将并发请求分散到独立进程，减少了 Python event loop 内部的 I/O 调度竞争。

> **核心结论**：PROXY_WORKERS 的唯一价值是降低高并发下的 TTFT（排队效应），对串行请求无影响，对 TPS 无影响。

## 5. 分析与结论

### 5.1 资源消耗规律

- **内存**: 每个 worker 进程占用 ~65 MB RSS
  - workers-1: ~65 MB, workers-4: ~295 MB, workers-16: ~1073 MB
  - workers-64: ~4186 MB, workers-128: ~8338 MB
- **CPU**: 空闲时 worker 数越多基础 CPU 占用越高（workers-128 空闲 10%）
- **内存与输入输出 token 数无关**: 128/128 和 512/512 场景下资源占用几乎一致

### 5.2 TTFT 影响规律

- **串行（低并发）**: 所有 worker 配置 TTFT 几乎相同（~105-107ms），proxy 额外开销 2-4ms
- **高并发下 worker 数是决定因素**:
  - workers-1 在并发=50 时 TTFT P95 显著升高（排队效应）
  - workers-4 能显著改善高并发 TTFT
  - workers-64/128 进一步降低 P95，但边际收益递减
- **TTFT 与输入 token 数无关**: 因为 mock prefill 时间固定为 100ms
  - 真实引擎下，输入越长 prefill 越慢，TTFT 差异更大

### 5.3 TPS 影响规律

- **TPS 在所有配置下几乎不变** (~33.2 tok/s):
  - 增加 worker 数不改变单请求 TPS
  - TPS 由后端引擎决定，proxy 不引入额外延迟
- **TPS 与输出 token 数无关**: 128 tokens 和 512 tokens 产生相同 TPS
- **系统 TPS（吞吐量）= 并发 × 单请求 TPS**
  - 系统吞吐量受并发能力限制，worker 越多支持并发越高

### 5.4 最佳实践建议

| 场景 | 推荐 Workers | 理由 |
|------|------------|------|
| 低并发 (≤5) | 1-4 | TTFT 无差异，节省内存 |
| 中并发 (5-20) | 4-16 | 有效降低 TTFT P95 |
| 高并发 (20-50) | 16-64 | 显著降低排队延迟 |
| 极高并发 (>50) | 64-128 | 需权衡 8GB+ 内存开销 |

### 5.5 关键结论

1. **增加 Worker 的核心价值是降低高并发 TTFT**（排队效应），不影响 TPS
2. **内存开销线性增长**: ~65 MB/worker，128 workers 需要 ~8.3 GB
3. **4 workers 是最佳性价比选择**: 285MB 额外内存即可显著改善并发 TTFT
4. **资源消耗与输入输出 token 数无关**: proxy 本身不消耗大量 CPU/内存
5. **串行 TPS ≈ 直连 TPS**: proxy 对流式传输几乎零开销
