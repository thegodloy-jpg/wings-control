## 5. 分析与结论

### 5.1 资源消耗

- **内存 (RSS)**: 每增加一个 worker 进程，约增加 55~65 MB RSS
- **CPU**: 空闲时几乎不占 CPU；负载时 CPU 使用与并发数和 worker 数正相关
- Worker 数超过 CPU 核数时，CPU 调度开销增加但不会额外消耗更多 CPU

### 5.2 TTFT 影响

- Proxy 对 TTFT 的额外开销主要来自进程间路由和网络转发
- 在低并发下，worker 数量对 TTFT 影响很小
- 在高并发下，worker 不足会导致请求排队，显著增加 TTFT

### 5.3 TPS 影响

- Proxy 对每请求 TPS 几乎无影响：所有配置串行 TPS 均为 ~33.2 tok/s，与直连基线一致
- 系统 TPS（并发50）在所有配置下稳定在 ~1,650 tok/s，表明 Workers 数量不影响 token 传输速率
- TPS 的瓶颈在后端引擎的 token 生成速度，proxy 仅做 SSE chunk 零拷贝转发
- **结论：增加 Workers 的核心收益体现在 TTFT 排队延迟的降低，而非 TPS 提升**

### 5.4 最佳实践建议

- **推荐配置 4~16 Workers**：以约 300MB~1GB 的内存代价，获得高并发场景下最显著的 TTFT 改善
- workers-4 的"每 MB 内存换取的 P95 改善"最高（0.77 ms/MB），性价比最优
- 128 Workers 虽然在高并发 TTFT 上表现最好（P95=225ms），但内存占用 8.3GB，边际收益递减
